# 🔎 Incident Copilot

### RAG-система для технической поддержки и расследования инцидентов

> Годовой проект по теме **«RAG-система / дообучение LLM под домен»**

---

## 📌 Итоговая тема

**Разработка RAG-системы для технической поддержки и диагностики программных инцидентов на основе технической документации, runbook-инструкций и истории предыдущих инцидентов.**

Проект объединяет два направления:

- Question Answering по технической документации ПО;
- поиск и анализ информации из корпоративной базы знаний, технической поддержки и истории инцидентов.

Цель проекта — создать **Incident Copilot**, который сможет не просто отвечать на вопросы по документации, а помогать инженеру диагностировать реальные технические проблемы на основе найденных источников.

## 💡 Идея проекта

При эксплуатации программных систем инженерам приходится искать информацию сразу в нескольких источниках:

- технической документации;
- внутренних инструкциях и runbook'ах;
- тикетах технической поддержки;
- отчётах о предыдущих инцидентах;
- postmortem-разборах.

Обычный поиск по ключевым словам часто не позволяет быстро найти решение, а LLM без доступа к актуальной базе знаний может генерировать недостоверные ответы.

Мы хотим построить RAG-систему, которая по описанию проблемы сможет:

1. найти релевантные части технической документации;
2. найти похожие прошлые инциденты;
3. подобрать подходящие инструкции и runbook'и;
4. сформировать возможные причины проблемы;
5. предложить последовательность диагностических действий;
6. предоставить ссылки на использованные источники;
7. отказаться от уверенного ответа, если в базе недостаточно информации.



### Пример запроса

> После нового deployment API начал периодически возвращать `503`, при этом выросла latency PostgreSQL. Какие могут быть причины и что проверить?

Система должна найти похожие инциденты и релевантную документацию, после чего сформировать **обоснованный ответ с диагностическими шагами и ссылками на источники**.

## 📚 Данные

Для проекта планируется использовать несколько типов открытых данных.

### Техническая документация

В качестве основной базы знаний можно использовать документацию популярных open-source систем:

- Kubernetes;
- PostgreSQL;
- документацию других программных продуктов и инфраструктурных инструментов.



### Technical Question Answering

Для построения baseline и оценки retrieval/QA планируется использовать **IBM TechQA** — датасет с техническими вопросами и корпусом технической документации.

### Инциденты и Root Cause Analysis

Для поиска похожих проблем и анализа причин планируется рассмотреть:

- **RCAEval** — benchmark с размеченными случаями отказов микросервисных систем;
- публичные engineering postmortem'ы;
- открытые incident reports;
- собственный набор runbook'ов и сценариев инцидентов.

В результате база знаний будет состоять из нескольких логических частей:

```text
Knowledge Base
├── Technical Documentation
├── Runbooks
├── Support Knowledge
└── Historical Incidents / Postmortems
```

## 🔬 Исследовательская часть

В рамках проекта планируется сравнить несколько вариантов построения системы:


| Подход                 | Описание                                                         |
| ---------------------- | ---------------------------------------------------------------- |
| **LLM baseline**       | Ответ без дополнительного контекста                              |
| **Naive RAG**          | Dense embeddings + vector search                                 |
| **Hybrid RAG**         | Dense search + BM25                                              |
| **RAG + Reranker**     | Дополнительное ранжирование найденных документов                 |
| **Advanced RAG**       | Metadata filtering, query rewriting, разные типы источников      |
| **Incident-aware RAG** | Отдельный поиск по документации, runbook'ам и прошлым инцидентам |


Дополнительно планируется исследовать методы снижения hallucinations и способность системы **не отвечать на вопрос**, если найденных источников недостаточно.

## 🧪 Дополнительные эксперименты

При достаточном времени планируется реализовать:

- Hybrid Search;
- Cross-Encoder / LLM Reranking;
- Query Rewriting;
- metadata-aware retrieval;
- version-aware retrieval;
- поиск похожих инцидентов;
- hallucination detection;
- confidence score;
- механизм abstention;
- adversarial-тестирование RAG-системы.

В adversarial-набор могут входить вопросы, ответа на которые нет в базе, противоречивые документы, устаревшая документация, похожие, но нерелевантные инциденты, разные версии одного ПО и prompt injection внутри документов.

## 🎯 Ожидаемый результат

Итогом проекта должна стать работающая **RAG-система для помощи в диагностике технических инцидентов**, способная работать сразу с несколькими источниками знаний:

**техническая документация + runbooks + база поддержки + история инцидентов.**

Помимо работающего приложения, проект предполагает полноценную экспериментальную часть: оценку retrieval и generation, сравнение различных RAG-подходов, анализ ошибочных ответов и исследование способов снижения галлюцинаций.

---



## 🚀 Почему это интересно

Большинство простых RAG-систем решают задачу:

> **вопрос → поиск по документам → ответ**

В данном проекте рассматривается более сложный сценарий:

> **описание технической проблемы → поиск документации + поиск похожих инцидентов + поиск runbook'ов → анализ найденных источников → диагностическая рекомендация**

Это делает проект близким к реальным задачам **DevOps, SRE и технической поддержки** и оставляет возможность в дальнейшем развить его в самостоятельный B2B-продукт.
